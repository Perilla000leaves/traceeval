# 一次「评测用例引用已删除工具」的排查

> 这是一次真实排查的脱敏记录。工具名做了泛化，机制与数字保留。
> 它说明的是：**评测集本身也需要被测**。

## 现象

评测集共 58 条用例，其中 3 条**每次都失败**，而且失败得很"稳定"——不是偶发：

| 用例 | 期望工具 | 现象 |
|---|---|---|
| `d05-*-detail` | `query_*_fill_detail` | 轨迹里没有这个工具 |
| `d06-*-detail` | `query_*_click_detail` | 轨迹里没有这个工具 |
| `f02-*-requested-fields` | `query_*_fill_detail` | 轨迹里没有这个工具 |

`score` 给出的原因是 `missing_tool`，**看起来像"模型没调对工具"**。

## 排查

1. 先看轨迹：模型实际调的是 `query_*_stage_detail`（一个名字相近但不同的工具）；
2. 再查注册表：重构时 `fill_detail` 与 `click_detail` **被合并**成 `stage_detail`，旧名已从注册表删除；
3. 回头查用例：这 3 条的 `expected_tools` 还写着**重构前的名字**。

也就是说：**用例在测一个已经不存在的工具**，它永远不可能通过。失败原因不是模型行为，而是用例过期。

## 影响

- 3 / 58 ≈ 5.2% 的用例恒失败，把通过率**系统性压低约 5 个百分点**；
- 更麻烦的是**它污染了归因**：每次跑完都能看到这几条 `missing_tool`，看多了就自动忽略，
  真出现"模型没调对工具"时反而不会警觉；
- 如果这次把通过率 92% 当成基线去判断一次改版"有没有提升"，结论会被这 5 个点带偏。

## 根因

**用例里的工具名是硬编码字符串，和注册表没有任何联动。**

工具清单在三个地方各有一份（注册表、Agent 白名单、实现），用例集是第四份——重构只改了前三份，
第四份没人 review，也没人跑断言。

## 修法

两层：

1. **单一事实源**：用例里的工具名从注册表派生，或至少在加载时校验
   ——`expected_tools` 里的每个名字必须能在注册表里查到，查不到直接**报错而不是判失败**；
2. **注册表三方断言**：注册表 / 白名单 / 实现三份名单在导入期做一致性检查，
   缺 spec、孤儿工具、实现参数对不上都直接抛错（见 `orchestrator/registry.py`）。

第 1 条是关键：**"引用了不存在的工具"应该是一个加载期错误，而不是一条永远失败的用例**。
把配置错误伪装成测试失败，是评测系统里最贵的一类设计错误——它看起来像"模型不行"。

## 教训

| 教训 | 具体做法 |
|---|---|
| 评测集也会过期 | 用例里的标识符必须来自单一事实源，加载时校验 |
| 恒失败的用例比没有用例更糟 | 它训练团队忽略红灯；应当让"不可能通过"在加载期暴露 |
| 通过率必须可解释 | 报通过率时同时报"哪些用例恒失败、为什么" |

## 在这个仓库里怎么落地

- `orchestrator/registry.py`：三方一致性断言，导入期失败；
- `traceeval` 的 `forbid_tools` / `expect_no_calls`：把"不该调用"也变成可断言项；
- `diagnose`：把"稳定失败"单独列出来——**稳定失败优先怀疑用例，而不是模型**。
