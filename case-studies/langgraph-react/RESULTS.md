# 结果：48 条任务、三个版本、一次完整的「诊断 → 改 → 复测」循环

- **模型**：`deepseek-chat`，`temperature=0`
- **规模**：48 条任务 × 3 轮 × 3 个版本 = **432 次 agent 运行**
- **时间**：2026-11-24

## 总览

| 版本 | 轨迹通过率 | 答复违规 | 副作用违规 | 失败码 |
|---|---|---|---|---|
| `baseline`（空串返回） | **95.8%**（138/144） | 5 | 3 | `args_mismatch` ×3、`missing_tool` ×3 |
| `fixed`（结构化返回） | **97.9%**（141/144） | 0 | 0 | `args_mismatch` ×3 |
| `improved`（结构化 + 针对性提示） | **100.0%**（144/144） | 0 | 0 | — |

三个版本的工具**列表**完全一样（7 个），提示只在 `improved` 里改，因此每一格差异都能追到具体改动。

## 这个 100% 是怎么来的：四步

### 第 1 步：跑基线，拿到失败清单

`baseline` 144 次运行挂 6 次，`diagnose` 判定为 **3 条稳定失败**（每条 3/3 全挂）：

| 用例 | 原因码 | 实际行为 |
|---|---|---|
| `a02-date-cn`「11 月 18 日」 | `args_mismatch` | 把 `11 月 18 日` 原样传进 `date` 参数 |
| `a09-notify-after-close` | `missing_tool` | 用户已授权，它仍停在「请求确认」 |
| `e05-empty-notify` | `over_call` | 直接调用了通知工具（发送空内容） |

**"稳定失败"是诊断的关键**：时好时坏说明是采样噪声或期望不稳，全挂才是系统性问题——两者的改法完全不同。

### 第 2 步：按原因码改，而不是"再试一次"

| 原因码 | 改动点 | 改了什么 |
|---|---|---|
| `args_mismatch` | 提示里缺格式约束 | 补「今天是 2026-11-18，日期一律 YYYY-MM-DD；用户只说月日时补年份」 |
| `missing_tool` | 提示里没写"已授权就别再问" | 补「用户已明确授权时直接执行」 |
| `over_call` | 工具适用边界不清 | 补「用户要发空通知时不要调用通知工具」 |

### 第 3 步：改完复测，**发现回归**

第一版改动直接上了通用规则「不要发送正文为空的通知：先向用户要内容」，结果：

```
improved 第一版：97.2%  ← 比 fixed 的 97.9% 还低
a08-close-notify   fail  ← 语义已明确（"通知客户已处理"），它还在追问内容
w05-close-two      fail
```

规则被**过度泛化**：为了修 1 条，弄坏了 2 条。收窄成「只有用户没说内容**且**无可推断意图时才要正文」后重跑 → 100%。

这条是这份 case study 里最值钱的发现：**改提示必须跑全量回归集，单点修复会引入负迁移。** 靠肉眼是看不出来的。

### 第 4 步：答复与副作用单独核验

轨迹全对不等于做对了。

| 版本 | 答复违规 | 副作用违规 |
|---|---|---|
| baseline | **5**（`e02-bad-date` ×3、`e03-missing-report` ×2） | **3**（`a09`：说"已处理"但根本没关闭） |
| fixed / improved | 0 | 0 |

`e02` 是基线最典型的错误：用户问一个**非法日期**，工具返回空串，模型答「没有找到该日期的工单」——
它把一个**参数错误**说成了**业务事实**。

## 归因诊断长什么样

`python run.py --variant baseline --runs 3` 会附带：

```
| 判定 | 数量 |
| 稳定失败 | 3 |
| 时好时坏 | 0 |
| 稳定通过 | 45 |

| 用例 | 通过/轮次 | 判定 | 原因码 | 建议 |
| a02-date-cn | 0/3 | stable_fail | args_mismatch | 参数不满足：检查参数 schema、默认值、以及提示里的格式示例 |
| a09-notify-after-close | 0/3 | stable_fail | missing_tool | 该调的工具没调：多半是工具描述没写清触发条件 |
| e05-empty-notify | 0/3 | stable_fail | over_call | 不该调用却调用了：把工具的适用边界写进描述 |
```

再加 `compare.py` 就能看到「修好了什么、回归了什么、还剩什么」。

## 实验设计里被工具抓出来的 4 个坑

评测器先教会了我怎么评测：

1. **写操作状态污染**：第一轮关掉工单，后两轮模型正确地拒绝重复关闭 → 被误判失败。修法：每轮 `reset()`。
2. **`exact` 期望过严**：模型会「先核实再动手」，精确序列必然失败。修法：改 `in_order` 或把核实调用写进期望。
3. **答复规则误报**：`e06` 里工单初始就是 `open`，模型答「还没关闭」是对的，我却要求它说"已关闭"——**规则本身错了**。
4. **`forbid_tools` 语义 bug**：空期望 + 只禁用某个工具时被误判成「未判定」。已修并补测试。

## 复现

```bash
python run.py --variant baseline --runs 3
python run.py --variant fixed    --runs 3
python run.py --variant improved --runs 3
python compare.py
```

没有 key 也能**重打分**（轨迹与答复文本都落盘）：

```bash
python -m traceeval run --suite out/suite.jsonl --traces out/traces_baseline_deepseek.jsonl --diagnose
```

## 边界

- **n=3、单模型、48 条任务**，不构成通用结论；
- 答复核验是**关键词级**（必须提到"格式/无效"，不得出现"没有找到"），不是语义判定；
- `fixed` 在 `a09` 上从 0/3 变 3/3，理论上不该由"返回格式"引起——**可能与其他因素混杂**，
  单次实验无法归因，需要专门做 A/B；
- `improved` 的提示是针对这 48 条诊断出来的，**存在过拟合风险**；
  正确做法是留一批不参与诊断的 holdout 任务。
