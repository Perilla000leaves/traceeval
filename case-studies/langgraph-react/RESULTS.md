# 结果

- **模型**：`deepseek-chat`，`temperature=0`
- **规模**：12 条任务 × 3 轮 = 每个版本 36 次运行
- **时间**：2026-11-24
- **成本**：不足 $0.01

## 总览

| 指标 | baseline | fixed | 差异 |
|---|---|---|---|
| 轨迹通过率（已判定） | **100.0%**（36/36） | **100.0%**（36/36） | 无 |
| 答复错误 | **4 / 36**（11.1%） | **0 / 36** | −11.1pp |
| 副作用违规 | 0 | 0 | 无 |
| 假成功调用 | 0 | 0 | 无 |
| P50 时延 | 1.7s | 1.7s | 无 |

## 结论一：工具契约没改变调用序列

两版轨迹通过率完全一样。原因是 DeepSeek 的默认行为很稳：**每次动作前先核实**。

- 工单不存在时，它先 `lookup_ticket`，看到空/错误就停，不会重复调用；
- 工单已关闭时，它拒绝再关一次，而是反问确认；
- 日期非法时，它调用一次 `list_tickets` 就停。

所以"空串导致模型疯狂重试"这个假设，**在 DeepSeek 上不成立**。脚本化模型时代能看到的重试，
在真模型这里被"先核实"的习惯挡掉了。

## 结论二：但答复错了 11%

轨迹全对，答复却有 4 次给了错误结论——全部集中在"错误路径"任务：

```
t06（查 2026-13-45 的工单）
baseline 答复：「查询已完成，但返回结果为空——没有找到 2026-13-45 的工单。」
fixed  答复：「查询失败：日期格式不正确（2026-13-45）。」
```

用户问的是一个**非法日期**，基线工具层把它和"当天没有工单"混成同一个返回值（空串），
模型于是给出了一个它无从知道的结论。修复版显式返回 `invalid_date`，答复就正确了。

`t10`（导出无数据月份）同理。

## 结论三：这个差异用「调用序列」根本测不出来

两版轨迹一模一样，假成功 0、重复调用 0、顺序 0——**只看轨迹，两版无法区分**。

要看见它，必须再加一层断言：

| 层次 | 能不能发现这个缺陷 |
|---|---|
| 工具调用序列 | ❌ |
| 副作用核验 | ❌（这次真的没有副作用） |
| 答复关键信息校验 | ✅ |

这是 traceeval 的边界，也是这份 case study 最有价值的一条：**轨迹评测能证明"做了什么"，
证明不了"说对了没有"**。

## 实验设计里被评测器抓出来的三个坑

这三个坑都不是"模型不行"，而是**评测本身设计错了**：

1. **写操作任务被状态污染**
   第一轮把工单关掉后，后两轮模型看到"已关闭"，正确地拒绝重复关闭 → 被判失败。
   修法：每轮运行前 `data.reset()`。这正是"写操作不能重复评测"的实证。

2. **`exact` 期望过严**
   模型会先核实再动手（`lookup_ticket -> close_ticket -> notify_customer`），
   期望写成 `["close_ticket", "notify_customer"]` 的精确序列就必然失败。
   修法：改成 `in_order`（必要调用按序出现即可），或在期望里显式写上前置核实调用。

3. **"看起来通过"掩盖了错误**
   第 2 轮跑完时两版都是 90%，差点写成"无差异"收工；查了逐条轨迹才发现失败全来自坑 1。

## 复现

```bash
# 有 key：重跑
python run.py --variant baseline --runs 3
python run.py --variant fixed    --runs 3

# 没有 key：用录好的轨迹重新打分（不需要模型）
python -m traceeval run --suite out/suite.jsonl --traces out/traces_baseline_deepseek.jsonl
```

## 边界

- 只有 12 条任务、一个模型、一个温度，**不构成通用结论**；
- 「答复错误」是关键词级检查（必须提到"格式/无效"，不得出现"没有找到"），不是语义判定；
- 结论只说明：**在这个模型上，工具契约的收益体现在答复质量，而不是调用序列**。
  换成更弱的模型或更长的工具链，结论可能不同——那正是下一步要测的。
